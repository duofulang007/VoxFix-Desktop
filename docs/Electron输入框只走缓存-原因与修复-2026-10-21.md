# Electron 输入框只走缓存 — 原因与修复（1.6.4.0，2026-10-21）

## 现象

在 WorkBuddy 的输入框里听写，文字不进光标处，而是全部落进「未上屏缓存」（左侧胶囊 → 复制按钮）。
微信、Zen 浏览器、记事本等输入框正常，边听边出。

## 根因：UIA 被当成了准入条件

旧链路的判定是二值门：

```
HasEditableTarget()  →  false  →  Pause("没有可确认的输入框")  →  文字全部进 recovery（缓存）
```

`HasEditableTarget` 依赖 UI Automation：取 `AutomationElement.FocusedElement`，要求
`ControlType ∈ {Edit, Document, ComboBox}`、`HasKeyboardFocus = true`、且该节点能沿祖先链
找到目标窗口的 HWND。

WorkBuddy 是 Electron（`D:\workbuddy\WorkBuddy.exe`，多进程 + `sandbox-center.exe`，
窗口类 `Chrome_WidgetWin_1`，子窗口 `Intermediate D3D Window`）。实测它的 UIA 树：

| 阶段 | WorkBuddy 暴露的节点 | 结果 |
|---|---|---|
| 无障碍未激活 | 1 个 `Pane`（`Intermediate D3D Window`） | 0 个可编辑节点 → 判「没有输入框」 |
| 被激活后 | 2 个 `Pane` + 1 个 `Document`（name=WorkBuddy），`HasKeyboardFocus=False`，`ValuePattern.IsReadOnly=True` | 仍判不可编辑；这个 Document 是 Chromium 给整个网页的**占位答案**，不是光标所在的 composer |

即：**Chromium 关着无障碍时，UIA 不是「没说话」，而是「说了假话」**——它把整个窗口描述成
一个只读文档。任何以 UIA 为门禁的实现，都必然把 WorkBuddy 判成「不能打字」。

另一个坑（本次踩到）：对这个 Chromium provider 调 `FindAll` / 读 `FocusedElement`
**会让调用进程挂死**。同一个查询在 `powershell.exe` 里 6 ms 返回，在独立 exe 里
（同样的 64 位 STA、同样的 API 顺序）直接不返回，探针卡死三次。

## 修复

### 1. 判定从二值改成三态

```
TargetKind { ReadOnly, Unknown, Editable }
Deliverable(kind) = Editable || Unknown     // Unknown 也送字
```

- `Editable`：UIA 明确给出可写 Edit/Document/ComboBox → 送。
- `ReadOnly`：UIA 明确给出只读文本框，或焦点在真正的非文本控件（按钮等）→ 仍进缓存（保留原有保守行为）。
- `Unknown`：窗口是「粗粒度宿主」，它的树描述不了光标 → **不再拦**，按光标送字。

### 2. 粗粒度宿主按窗口类名判定，不碰 UIA

```csharp
Chrome_WidgetWin_*            // Chromium / Electron / CEF / Edge / Chrome
FLUTTER_RUNNER_WIN32_WINDOW   // Flutter
CEF-OSC-WIDGET                // CEF 覆盖层
TaskManagerWindow             // 任务管理器（自绘外壳）
```

类名是 `GetClassName` 取的，**同进程内、瞬时、不会挂**，所以这类窗口完全不进 UIA 分支，
既避免误判也避免挂死。

> 曾试过「树里没有文本宿主就算粗粒度」，会把「只有一个按钮的普通对话框」误判成粗粒度，
> 已放弃；结构判据不可靠，类名可靠。

### 3. 其余窗口的 UIA 查询加 300 ms 熔断

```csharp
ClassifySafe(): Task.Run(Classify) vs Task.Delay(300)
超时 → 记入 stalledWindows，本次录音不再问该窗口，按 Unknown 送字
```

挂死的 provider 只会拖住一个线程池线程，采音与上屏不受影响。`BeginStream` 时清空熔断表，
代价是每次录音最多多等一次 300 ms。

### 4. 新增诊断模式（以后不必靠听写复现）

```
"bin\VoxFix Desktop.exe" --target-probe            # 当前前台窗口
"bin\VoxFix Desktop.exe" --target-probe WorkBuddy  # 指定进程主窗口（不抢前台）
输出：work/target-probe.txt
```

```
"bin\VoxFix Desktop.exe" --focus-test   # 只跑焦点判定回归（不需要麦克风/模型）
"bin\VoxFix Desktop.exe" --self-test    # 原有全量自检
```

## 实测证据

`work/uia-probe-20261021/target-probe-final.txt`（正式产物 1.6.4.0 跑出）：

| 应用 | 窗口类 | coarse | 判定 | 送字？ | 说明 |
|---|---|---|---|---|---|
| WorkBuddy | `Chrome_WidgetWin_1` | 是 | Unknown | **是** | 修复目标，以前必然缓存 |
| 微信 | `Qt51514QWindowIcon` | 否 | Editable（焦点在 `mmui::ChatInputField` 时） | 是 | UIA 正常，未受影响 |
| Zen 浏览器正文 | `MozillaWindowClass` | 否 | ReadOnly | 否 | 网页正文是只读 Document，本来也不该打字 |
| 任务管理器 | `TaskManagerWindow` | 是 | Unknown | 是 | 自绘外壳 |
| Nano | `FLUTTER_RUNNER_WIN32_WINDOW` | 是 | Unknown | 是 | Flutter |

回归（正式产物上复跑，均 PASS）：

- `--self-test`：`coarse-host delivery / read-only and non-text veto` 等全通过。
- `--focus-test`（真实 WinForms 窗口 + 真实 SendInput + 真实 UIA）：
  外部窗口的陈旧 UIA 焦点仍被拒；可写输入框恢复并注入；非输入窗口仍进缓存；
  回到旧框只续新字；新输入框被采纳；只读框仍进缓存；恢复后不重放；迟到音频留在缓存。

## 影响面：哪些「以前的输入框」不再进缓存

同一类问题（UIA 树描述不了光标）覆盖：

- 所有 Electron 应用：WorkBuddy、VS Code、Obsidian、Slack、Discord、Notion、飞书/钉钉桌面端、
  Postman、Teams 等（窗口类均为 `Chrome_WidgetWin_*`）。
- 所有 Chromium 浏览器里的富文本编辑器（页面内本来就靠光标送字）。
- Flutter 桌面应用。
- 自绘外壳（任务管理器这类）。

## 遗留风险（有意接受）

1. **粗粒度宿主里，焦点在按钮/链接上时也会送字**，字会掉进虚无（页面不接收）。
   这是 Win+H 的既有行为；换来的是「不再整段变缓存」。UIA 若可用（微信、Win32/WPF、
   Gecko 页面里的 input），仍按节点精确判定。
2. 浏览器里读文章时听写，文字不会进缓存（以前会）。原因同上。
3. 只读文本框（`ReadOnly = true` 的真 Edit）**仍然**进缓存，这条没放松。
