## 0. 一句话结论

**分工结合，但分界线不是「CPU 一半、GPU 一半」，而是「实时链路 vs 离线链路」。**

- 实时首遍流式（决定手感）：**CPU**，ggml/GGUF 路线，4–6 线程。
- 松手后二遍 / 标点 / 纠错（决定准确率）：**先 CPU 小模型**；只有引入 LLM 改写或重打分时才上 GPU。
- 离线批量评测（决定版本能不能发）：**GPU 优先跑吞吐**，同一批音频 CPU 也跑一遍做基准。

**不要一开始就做双后端。** GPU 流式只作为一条可切换的对照分支存在，不设成默认。

## 1. 这个结论建立在三条已有事实上

| 事实 | 数据 | 来源 |
|---|---|---|
| 首字延迟的地板是**算法**，不是算力 | 9700X 上 2/4/8 线程：529 / 522 / 514 ms，加 6 个线程只快 15ms；K60 是 618ms。桌面比手机快约 100ms 就是算力能贡献的全部 | 本机实测（安卓项目 2026-10-20） |
| 同一模型换运行时，桌面 CPU 差距可达 3–5 倍 | NeMo-Speech.cpp Q8_0、160ms 分块：桌面 CPU **27 ms/chunk（≈6× 实时）**，RTX 4090 **2.3 ms/chunk**；而 sherpa-onnx int8 的 160ms 档在社区实测要**约 9 个核**才跟得上实时，560ms 档 2 线程即可 | NVIDIA 官方 benchmark；Live-Subtitles 项目实测 |
| 手机上的死因（decode/audio = 1.14）在桌面上不成立 | K60 2 线程 1.143、4 线程 1.140 —— 那颗 ARM CPU 算力不够。9700X 有 16 线程且单核强数倍 | 本机实测 |

推论：**桌面版真正的决策变量不是「显卡还是 CPU」，而是「用哪个运行时」。** 运行时选错，GPU 也救不回来（int8 ONNX 在 CUDA 上大量算子回退 CPU，实测比 CPU 还慢）；运行时选对，CPU 就有 5 倍以上实时余量。

## 2. 分工表（这就是最终答案）

| 链路 | 设备 | 理由 | 可回退方案 |
|---|---|---|---|
| 麦克风采集 + VAD + 160ms 分块 | CPU（单线程，几乎不计） | 采集与 VAD 是音频线程，必须抖动小；放 GPU 只会增加一次拷贝 | — |
| **流式首遍 RNNT**（边说边出字） | **CPU**，4–6 线程 | 桌面 CPU 已有 6× 实时余量；不吃显存、不和游戏/浏览器抢卡、绕开 sm_120 全套坑、崩溃可热重启 | 一条 `--device cuda` 对照分支，仅用于证明「不是算力问题」 |
| 松手尾块补渲染 | CPU（复用同一 recognizer） | 尾块只有 1–2 个 chunk，GPU 反而多一次同步开销 | — |
| 二遍精修（SenseVoice 级） | CPU | 229MB 级离线模型，16 线程下几十毫秒；GPU 收益 < 30ms，不值得多一套依赖 | GPU（fp16） |
| 标点（CT-Transformer 31MB） | CPU | 纯文本模型，太小 | — |
| LLM 改写 / 术语重打分（可选功能） | **GPU** | 这是唯一真正吃显卡的部分（4B int4 约 2.5GB 显存）；桌面写代码/写文档，术语纠错价值最高 | CPU 上关掉，降级为词典替换 |
| **批量评测（174 条 + 后续语料）** | **GPU 优先** | 无延迟约束，只看吞吐；一次跑完 fp32/fp16/int8 三种精度做对照 | CPU（慢 5–10×，可过夜跑） |

一句话记法：**手上的字用 CPU 算，落盘的字用 GPU 算。**

---

## 3. 为什么首遍不上 GPU（把反对意见写清楚）

不是「GPU 没用」，是「在这台机器上不划算」：

1. **它改善不了用户能感知的那个指标。** 首字 P50 的地板是 RNNT 攒块 + 160ms 分块，实测加线程只快 15ms。GPU 最多再削掉几十毫秒，而代价是每次说话都要唤醒一次显卡上下文。
2. **int8 在 GPU 上常常更慢。** 公开实测（GTX 1070 上的 Nemotron/Parakeet 对照）：int8 导出的算子会回退到 CPU，比 fp32 还慢；要上 GPU 就得用 fp16/fp32，体积从 682MB 涨到 2.5GB。8GB 显存还要留给二遍和 LLM。
3. **sm_120 是新卡。** 5060 Ti 是 Blackwell（compute capability 12.0），需要 CUDA 12.8+，且 ONNX Runtime / sherpa-onnx 的预编译包必须带 sm_120 kernel，否则报 `no kernel image is available`。这条坑的排查成本远高于它带来的收益。
4. **它是后台常驻工具。** 语音输入应该像输入法一样「不存在」：不占显存、不打乱游戏帧率、风扇不转。把首遍放 GPU 会让「一边打游戏一边语音输入」变成两个程序抢卡。
5. **功耗与噪声。** 桌面不怕发热，但怕风扇。CPU 跑 4 线程 0.17 RTF 的功耗，远低于让独显从 P8 唤醒。

**什么情况下改判**：如果 P0 实测 9700X 上 CPU 的 RTF > 0.5，或首字 P50 > 800ms，那就说明这颗 CPU 也吃不消，此时再认真做 GPU 分支（并且必须用 fp16，不能用 int8）。

## 4. 测试方案（P0 → P3，每阶段有明确产出与门槛）

### P0 · 桌面 CPU 基线（半天，必须先做）

目标：拿到 9700X 上「真实可用的 RTF / 首字 / 松手延迟」，和官方 bench 对账。

- 两条运行时并排跑，**同一批 174 条固定音频**（直接复用安卓项目的金标口径：中文 CER、英文 WER、混说统一单元错误率、忽略标点）：
  - A：`sherpa-onnx 1.13.8` + `...-160ms-int8-2026-06-11`（安卓已验过的同一份包，可比性最好）
  - B：`NeMo-Speech.cpp` + GGUF（Q8_0 742MB / Q4_K_M 473MB）
- 每档都跑 2 / 4 / 6 / 8 线程，记录 `decode/audio`、首字 P50/P95、峰值 RSS、冷启动加载时间、CUDA 是否被误启用。
- **必须按 20ms 真实节奏投递**（安卓脚本里已有 `Fixed audio was fed faster than real time` 断言，照搬），整段灌入测出来的 RTF 没有意义。

**通过门槛**：至少一条路线 RTF ≤ 0.35（4 线程）、首字 P50 ≤ 550ms、峰值 RSS ≤ 1.6GB。
**不通过** → 直接进 P2 讨论 GPU，别在 CPU 上调参浪费时间。

### P1 · GPU 流式对照（只做一条曲线，不做产品分支）

目标：用数据证明「首遍不搬 GPU」这个判断，而不是靠推理。

- 只用 fp16/fp32（禁 int8），CUDA 12.8+ 构建，验证 sm_120 是否有 kernel。
- 记录：每 chunk 解码耗时、首字 P50、显存增量、`nvidia-smi` 的功耗/频率跳变、与「同时跑一个 3D 程序」时的抢占情况。

**预期结论**（若不符合就如实改方案）：GPU 把 27ms/chunk 降到 3–5ms，但首字只快 30–80ms，显存 +1GB 以上 ⇒ 不设为默认。
**唯一保留用途**：低端机兜底 + 未来「一边听会议一边本地大模型摘要」才用。

### P2 · 二遍与纠错的落点

- 先把安卓的二遍 + 标点原样搬到桌面（CPU），量「松手 → 上屏」的 P50/P95。目标 ≤ 200ms（安卓是 75ms，桌面没有 IME commit 开销，应该更好）。
- 只有在「LLM 改写真的显著降低术语/同音字错误」时才开 GPU 分支；用 int4 4B 级模型，显存预算 ≤ 3GB。

### P3 · 长时与压力

- 连续听写 30 分钟（会议模式）、跨应用注入、休眠唤醒、模型常驻内存、开机自启。
- 这一阶段才是产品级验收，前面几阶段只证明「算得动」。

## 5. 运行时选型（比设备选择更关键）

| 路线 | 优点 | 缺点 | 用途 |
|---|---|---|---|
| `sherpa-onnx`（ONNX Runtime） | 和安卓共用同一套包与评测口径；Python 改一行就能跑；生态成熟 | 1.13.8 的 Kotlin/C++ 侧不暴露 `hotwords`/`prompt_dictionary`/`language`（安卓已证实）；CPU 上 NeMo 通路偏重 | **P0 对照基线**、批量评测 |
| `NeMo-Speech.cpp`（ggml） | 官方、原生 C++/稳定 C ABI、CPU 上 27ms/chunk、**支持 cache-aware RNNT 的 word boosting**、有 `--language`、有实时采集与 benchmark 子命令 | 需引入第二套运行库；GGUF 需 Q8_0/Q4_K_M；Windows 建议源码构建 | **产品默认** |
| transcribe.cpp / CrispASR（ggml 分叉） | 多模型统一 | 非官方，接口不稳定 | 只作参考 |

**结论**：产品走 NeMo-Speech.cpp。它把安卓上丢掉的两个能力（按语言指定、热词/术语 boosting）都拿回来了 —— 而「术语准确」正是桌面写代码场景的最大价值点。评测期仍用 sherpa-onnx 保持和安卓同口径可比。

许可：模型 OpenMDW-1.1（不是 Apache-2.0），运行时 Apache-2.0，两者分开保留，安装包里各自带 NOTICE。

## 6. 目标架构（纯语音输入，不含键盘）

```
全局热键(按住/切换) ──► WASAPI 16k mono 采集 ──► silero VAD ──► 160ms 分块
                                                                    │
                                                    流式首遍 RNNT（CPU, 4–6 线程）
                                                                    │
                                          悬浮字幕条（置顶, 不抢焦点, 逐字追加）
                                                                    │
                                              松手 ──► 尾块补完 + 二遍/标点（CPU）
                                                                    │
                                              文本注入（焦点窗口）──► 完成/撤销(Ctrl+Z 兜底)
```

工程上真正难的三件事，**都不是 ASR**：

1. **文本注入**。Windows 没有 Android 的 `InputConnection.commitText` 等价物。优先 `SendInput` + `KEYEVENTF_UNICODE` 逐字注入；对 Electron/VSCode/终端这类吃原始按键的应用准备第二条路（剪贴板 + `Ctrl+V`，用完还原）；IME 处于中文态时的候选窗干扰要单独验。
2. **不抢焦点**。悬浮条必须 `WS_EX_NOACTIVATE`，否则一显示就把注入目标窗口的焦点抢走，字打到空气里。
3. **常驻成本**。空闲内存目标 ≤ 250MB、模型空闲 30 秒释放（安卓已验证这套「用后释放」策略可行）、冷启动 ≤ 1.5 秒（或用预热 + 首次说话时并行加载）。

可直接复用的资产：174 条固定音频与金标、CER/WER 计分口径、`tools/asr_eval.py` 的骨架、二遍/标点模型、`SpeechSecondQueue` 的队列与取消语义、VAD 边界补 160ms 的经验。

| 指标 | 门槛 | 现状参照 |

| 显存（默认路径） | **0** | —— |
| 显存（GPU 分支） | ≤ 1.5GB | fp32 ONNX 包 2.5GB，超预算 |

## 8. 不做什么

- 不做「双后端自动切换」。切一次要重载 682MB 权重，冷启动 5 秒，得不偿失。
- 不在首版做 LLM 润色。安卓上已因收益不明移除（`docs/仓库清理-2026-10-18.md`），桌面先证明准确率缺口再谈。
- 不用 80ms 分块换低延迟。首字地板在算法不在分块，80ms 只会更碎、RTF 更差。
- 不因为「显卡闲着」就把首遍搬上去。

## 9. 第一步（今天就能跑）

1. 建独立 venv（**不要复用 VoxFix 的 `.venv`，它是 1.13.6，评测口径要求 1.13.8**），装 `sherpa-onnx==1.13.8`。
2. 从 `hf-mirror.com/csukuangfj2/...-160ms-int8-2026-06-11` 拉包（GitHub 直连约 45KB/s，必须走镜像 + 多线程分块），校验四个文件的 SHA-256（安卓实测文档里有全部哈希）。
3. 抄 `tools/asr_eval.py` 的骨架 + 20ms 节奏断言，跑 174 条 × 2/4/6/8 线程，输出 `report-p0.json`。
4. 同一批音频跑 `NeMo-Speech.cpp`（Windows 用 `install.ps1`，`--channel nightly` 拿最新预编译；或 `--source` 源码构建），记录 27ms/chunk 这个官方数字在 9700X 上是否成立。
5. 两张表放一起，P0 门槛过 → 直接进 P1/P2；不过 → 回来改方案。

预计 P0 半天（下载占一半时间），P1 两小时，P2 一天。
