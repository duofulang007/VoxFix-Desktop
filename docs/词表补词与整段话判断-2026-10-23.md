## 为什么改

用户问"跑测试看哪些，内容是明显需要加入词典的"。做法是：用现行生产链路重跑旧 174 条固定语料，
把"参考文本里是拉丁词、但没被正确识别"的位置全部列出来，再判断哪些是词表能解决的。

加词前的重跑（`F:/VoxFixTrain/eval/legacy-dict-20261023.json`）里，剩下的拉丁词错误只有这些：

| 参考 | 实际输出 | 条数 |
|---|---|---|
| VoxFix | `vox fix` / `voox fix` | 3 |
| Kotlin | `cotland` / `coland` | 2 |
| git | `get`（`get status` / `get commit`） | 2 |
| API | `app` | 1 |
| JSON | `js on` | 1 |
| cache | `cash` | 1 |

外加 4 条只是大小写不同（`wifi` / `python` / `github` / `api`），评分不算错，但用户看到的是错的写法。

## 补进出厂词表的

`dictionary.json`（备份在 `work/dictionary.json.20261023-backup`）：

| 词 | 新增错法 |
|---|---|
| VoxFix | `vox fix`、`voox fix`、`voxfix`、`v fix`、`box fix` |
| Kotlin | `cotland`、`coland`、`codelin`、`kotlin` |
| API | `a p i`、`api i`、`api` |
| PDF | `p d f`、`pdf` |
| WiFi | `wifi`、`wi fi`、`why fi` |
| Python | `python` |
| JSON | 追加 `js on`、`json` |
| GitHub | 追加 `github` |
| git status / git commit | `get status`、`gi status` / `get commit`、`gi commit`（`context: zh`） |

`hotwords` 追加 `VoxFix`。

后 6 条（VoxFix / Kotlin / API / PDF / WiFi / Python）**不写 `context`**，因为大小写与写法规范在任何语言下都该生效；
`git status` 这类是真词冲突（`get status` 在英文里也讲得通），只在含中文的整段话里替换。

## 故意没加的

| 词 | 实际输出 | 不加的理由 |
|---|---|---|
| cache | `cash` | `cash` 是正常英文词，"I need cash" 会被改成 cache |
| API | `app` | 中文句里 "这个 app 挺好用" 远多于说 API，规则会把正常句子改坏 |
| 我 | `或` | 不是词表问题，是识别本身错字，词表没有线索可依 |

这三条要治只能动模型（更多技术术语数据），不是加词能解决的。

## 顺带修的两个"加词也不生效"

1. **中文规则其实是按分段判断的**。`apply_dictionary` 在分段解码后立刻执行，`context: "zh"`
   只看当前分段有没有中文；`这个API。返回的是。js on。数据。`里的 `js on` 那一段是纯英文，
   规则因此跳过。改成按整段话判断：`force=has_chinese(self.committed + text)`，已经说出来的中文也算。
   纯英文整段仍然不受影响（契约不变）。
2. **词典窗口保存会把所有规则写成 `context: "zh"`**。1.6.34.0 的 `DictionaryDialog.Save()` 写死
   `"context": "zh"`，用户在窗口里按一次保存，上面那 6 条"任何语言都生效"的规则会集体退化成仅中文，
   纯英文的 `Kotlin` / `VoxFix` 会重新变错。改成 `WordGroup.Context` 记住文件里的原值（缺省为空＝任何语言），
   保存时按原值写回。
