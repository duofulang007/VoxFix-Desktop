## 结论

SenseVoice 是 CTC 模型，sherpa 不支持热词，但在 ORT 层能拿到逐帧 logits，因此可以自研解码期偏置。
三个阶段全部通过闸门后按**救援通道**形态上线：生产主路径仍是 sherpa，只有定稿文本里出现
"读起来像词表词"的片段时，才用偏置解码器把这段音频复解一次，命中不了就原样保留。

| 阶段 | 闸门 | 实测 | 结果 |
|---|---|---|---|
| P0 复刻 | 与 sherpa 逐字一致（或 ≥99.5% 且差异可用 int8 解释）；解码 ≤2× | 24/24 句一致；全 174 条 170/174 句、99.854% 字符；p50 比值 1.15 / 1.12 / 1.02 | 通过 |
| P1 偏置 | 专项显著提升 + 三套零回归 | 专项术语命中 8/18→11/18（boost 2.0）；174 整句 139→142；封存 1,314 整句 699→699；误插 1 例 | 通过 |
| P2 接线 | 短句 p50 不退化 +10% 内；测试全绿 | 68 个普通段三档重复：救援开销 p50 **0.0 ms**（未命中直接跳过）；Python 测试 4 套全过 | 通过 |

## 特征契约（复刻 sherpa 的唯一正确版本）

`work/hotword-prototype/P0-report.md` 有完整推导，这里只留结论，因为**猜错的两个参数会让一致率
看起来有 95%+ 但其实是错的**：

- 模型 metadata `normalize_samples=0` ⇒ 波形先 **×32768** 再提特征；
- 窗函数 **hamming**（不是 knf 默认的 povey），`snip_edges=true`，`high_freq=0`；
- LFR(7,6)：输出 `1 + (T-1)//6` 帧，第 i 帧以第 `i*6` 帧为中心、两侧夹取边界（不是 FunASR 的补帧方式）；
- CMVN：`(x + neg_mean) * inv_stddev`，两个向量已是 560 维；
- ORT 必须用 `ORT_ENABLE_BASIC`：`ORT_ENABLE_ALL` 的融合会让 4–7 句低裕度粤语单字翻转。

## 偏置怎么工作

1. 热词写成 **所有可能的 token 切分**（`min_tokens + 1` 以内）再建 trie。
   只按最短切分建树会完全失效：`GitHub` 最短是 `gi|th|ub`，而模型实际发 `gi|t|th|ub`。
2. 解码维护"当前可能处于的前缀"集合，每帧给这些前缀的**下一个 token** 加 `boost`（原始 logit 单位，默认 2.0）。
3. 只有新 token 才推进前缀；blank 与 CTC 重复帧保持状态，所以偏置不随帧衰减。
   分支遇到不属于它的 token 就失效，同时始终允许从根重启，因此词可以在任意帧开始。
4. 前 4 帧是 language / EMO / event / itn 查询位，不参与匹配。

强度扫描（174 / 封存 1,314 / 专项）：boost 1.0、2.0、3.0 在两套大语料上整句数完全相同，
3.0 只在专项多救一个 `JSON`；**boost ≥8 会过冲**（`wififi`、`pythonthon`、`githubub`、`JSONN`），
上限卡 5。取 **2.0**。

## 生产接线

- `app/hotwords.py`：近音检测 + trie + 偏置贪心解码 + 惰性 ONNX 会话（新增文件，约 300 行）。
- `app/recognize.py`：定稿文本先过 `HotwordRescue.rescore`，再过个人词典与标点；草稿不做救援
  （草稿本来就会被修订，救援只会多花时间）。
- `dictionary.json` 新增 `hotwords` 字段。**只有显式写这个字段才会启用救援通道**，
  不写就完全不动（零开销、零新会话）。`rules` 兜底替换层保持原样，两层并存。
- 救援的接受条件（任一不满足就保留 sherpa 原文）：复解文本里出现的词表词**更多**、
  长度不短于原文 60%、没有中英以外的字符、任何异常都回退。
- 内存：额外 ONNX 会话约 **290 MB**（整进程 362 MB → 651 MB），因此**惰性创建**，
  首次真正需要救援时才建，闲置 180 秒自动释放；冷启动约 1.0 秒（进程内只付一次），
  之后每次救援 35–60 ms。

## 评测数据

| 语料 | 无偏置 | boost 2.0 | sherpa 生产 |
|---|---|---|---|
| 专项（旧 174 含术语的 14 条 / 18 个术语位） | 5/14 句，术语 8/18 | 8/14，11/18 | 5/14，8/18 |
| 旧 174 | 139/174 | **142/174** | 139/174 |
| 封存 1,314 | 699/1,314 | 699/1,314 | 696/1,314 |

174 上只有 5 句变化：`pyython→python`、`gitthub→github`、`a→api` 三句由错变对，
`gitHub→github` 仍算对，`J SON→JSON` 该句仍有别的错。其余 169 句逐字未变。

误插（没说的词被写出来）在 4,506 次解码里只有 1 例：`the main for engine system` → `I mean for Android system`，
比例 0.08%，且该句本来就不对。

## 已知边界（照实写，别当成回归）

- **首 token 就跑偏的救不回来**：`Kotlin`→`coattland`、`API`→`app`（`app` 是单个词表项）。
  解码期偏置进不去这条路径，需要声学层面的近似匹配，本轮不做。
- **词内多一个 token 的救不回来**：`WiFi`→`wiifi`。试过给 blank 加同等加成，能修好但会把词尾吃掉
  （`api→a`、`JSON→JS`），已否决。
- 专项集仍是替代品：旧 174 里含术语的 14 条，用户本人 20–30 个词的真实录音尚未提供。
  录音给到后可 `work/hotword-prototype/p1_eval.py --corpora terms` 直接重跑。
