# VoxFix Desktop：替代 Win+H 的技术路线

日期：2026-10-20。范围：选型与开发顺序；未修改应用代码、计分脚本、热键或系统设置。

## 推荐决策

现在最稳妥的工程路线是：**Windows 原生轻量悬浮条 + CPU 流式预览 + 句级终稿 + 本地纠错学习**。首版以现有 Zipformer 为即时预览基线；终稿先复用 SenseVoice 与 CT 标点作为对照，先评测已有 Nemotron 3.5 ASR 与新增 Fun-ASR-Nano；若中文/混说仍不够，再加入 Qwen3-ASR-0.6B，胜者才进入默认链路。每次只运行一个终稿引擎。

这属于基于当前证据的工程推荐，不是已经证明某个模型在用户真人语音上最优。Nemotron 不必放弃，也不应因为 NVIDIA 品牌预先锁为唯一引擎。不要将“用了某模型”与“有个人学习能力”绑定。

## 证据来自哪里

已阅读 WorkBuddy 的三个项目会话记录（旧 C 盘项目与当前 D 盘项目），以及本项目两份既有报告、tools/p0_*.py 和 work/p0 的原始 JSON。会话中曾先后建议 Nemotron 句末提交、Zipformer 两遍；最终取舍应回到用户需要的实时反馈、真人正确率与资源预算。

本轮核对硬件：注册表返回 AMD Ryzen 7 9700X；nvidia-smi 返回 RTX 5060 Ti、8151 MiB 显存、617.42 驱动。系统接口报告可用物理内存总量约 13.6 GiB、当时剩余约 2.8 GiB；这是运行时快照，不能据此断定 DIMM 安装容量。未完成麦克风型号、声学环境与真人口音评估。

既有原始数据可确认：Nemotron Q8_0 的 174 段共 671.86 秒音频，CPU 4 线程用时 40.72 秒，Vulkan 用时 23.92 秒；记录的 CPU 峰值 RSS 约 1.2GB。证明算得动，不证明比 Win+H 更准、更快。RTX 5060 Ti 为可选终稿加速资源，首版不要求常驻 GPU，更不要求升级显卡。

## WorkBuddy 结论需要修正的部分

1. **英文计分有缺陷**：tools/p0_score.py 的 normalize 先删除空白，units 随后才提取英文词，英文整句会粘成一个 token。现有 WER 与混说单元错误率不适合作最终选型；中文、英文、混说、数字格式与标点应分开重算。174 条整体结果还混入粤语等不同需求，不能称为“中文准确率”。
2. **首字数字不是完整产品延迟**：脚本保存的是已投递音频的样本进度，不是从麦克风开口到界面绘制的完整墙钟；部分循环在等待前检查输出，还存在一帧预喂差异。8 条 Zipformer 样本中一条直到尾部处理才出字，汇总时被排除。420/600/1060ms 只能作为当前配置的探索性结果。
3. **1060ms 不是模型不可突破的地板**：运行时、量化、解码配置与上下文均不同；sherpa int8 和 GGUF Q8_0 不是完全相同的推理产物。RTF 也不等于 CPU 占用百分比。
4. **两遍不是硬性定律**：若一个流式引擎在用户语料上同时满足快与准，就可以移除第二遍。终稿模型也未必比第一遍更准，必须测“修正多少、改坏多少”。
5. “pnc=off 仍有标点”单独不能证明另一运行时一定丢了标点：参数可能无效，权重导出/分词器也可能不同。已有链路本来有 CT 标点，应比较最终文本质量，不能把带标点条数当准确率。
6. Android 的已有链路可作为复用起点，不能替代 Windows 麦克风、跨应用输入与个人学习验收。按文件字节数相同也不能认定两份模型内容完全一致。

## 模型如何选择

| 层 | 首版选择 | 升级条件 |
|---|---|---|
| 即时反馈 | sherpa-onnx + 现有中英 Zipformer，CPU | Nemotron 或其他流式引擎在同一真人语料下同时改善实时延迟与终稿质量，且资源成本可接受 |
| 终稿对照 | 现有 SenseVoice + CT 标点，CPU | 先记录 Windows 真实基线，再决定是否保留 |
| Nemotron 3.5 ASR | 重点终稿候选；用已跑通的 transcribe.cpp 0.4.0 + Q8_0 先做对照 | 同音字、中英术语、数字、标点有真实净改善，再设默认；锁定模型与 DLL 的版本和校验值 |
| Fun-ASR-Nano | 优先新增的中文终稿与热词候选；先验证官方 Windows/GGUF 路径 | 热词在个人录音上改善术语且不污染普通词，再进入默认；本机性能未测 |
| Qwen3-ASR | 先测 0.6B 短句终稿，必要时才评估 1.7B | 本机实际显存、加载、尾延迟和中文收益达标后再启用；不能拿权重大小代替进程显存 |
| Whisper / 其他流式模型 | 当前不同时接入 | 前面候选均未满足明确需求时，按失败类别增加一个对照 |

NVIDIA 官方模型卡确认 Nemotron 3.5 是流式 ASR，支持普通话与词语增强等能力；并非必须部署聊天大模型。中文支持不等于对个人中文输入最优。[NVIDIA 模型卡](https://huggingface.co/nvidia/nemotron-3.5-asr-streaming-0.6b)

Qwen 官方提供 0.6B/1.7B、中文及方言、离线和流式能力；其官方包流式路径目前使用 vLLM，因此本项目先评估短句离线终稿，避免把服务框架带进首版热路径。CUDA/Blackwell 与 Windows 包兼容性仍须实测。[Qwen3-ASR 官方仓库](https://github.com/QwenLM/Qwen3-ASR)

Fun-ASR-Nano 官方提供热词示例，当前亦有 Windows/GGUF/CPU 路线。因此针对中文个人术语值得优先新增一次对照，不能仅沿用旧资料把它当成 GPU 离线方案；上游支持不等于本机已跑通。[Fun-ASR 官方仓库](https://github.com/QwenAudio/Fun-ASR)

## 产品与技术边界

建议 Windows 专用壳使用 C# / WPF 与 Win32，识别先复用现有 Python worker 做验证；打包前按实测选择直接调用 C ABI 或保留隔离进程，不先造通用插件框架。采集使用 WASAPI，按引擎要求重采样至 16k 单声道，保留短预录缓冲，端点检测与尾帧 flush 单独验收。

数据流：热键 → 采集/端点 → Zipformer 实时草稿 → 句级终稿（仅一个候选引擎） → 个人词与保守规范化 → 焦点检查 → 提交。

截图中的小浮窗适合作为交互参考：麦克风、拖动、关闭、设置，录音时有明确状态；展开可看到一句草稿与最近终稿。词库/纠错编辑放到独立可获得焦点的窗口，不能把所有控件强行设为不激活。

**首版在悬浮条显示草稿，按句把终稿提交到目标应用。** 避免不断用退格改写目标窗口里已落地的文本；用户一旦编辑、切换焦点或目标失效，待提交结果留在预览区。这样依然能边说边看，但目标应用的内容更稳定。若后续需要像输入法一样在目标输入框内实时组合，单独评估 TSF，不能声称 SendInput 已经实现通用组合文本。

Win32 的 WS_EX_NOACTIVATE 可避免悬浮条点击夺走前台；SendInput 受 UIPI 权限限制，不能保证输入管理员窗口。剪贴板兜底需要检查变更后再还原，避免覆盖用户并发复制。未提交文本应可恢复。[窗口样式](https://learn.microsoft.com/en-us/windows/win32/winmsg/extended-window-styles)、[SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)

“替代 Win+H”指产品功能。首版使用可配置且无冲突的热键；Windows 键组合为系统保留，不把原样接管 Win+H 作为前置条件。[RegisterHotKey](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-registerhotkey)

## 如何做到越用越准

第一层先做**个人词库与上下文偏置**：保存正确拼写、别名/读音、出现次数、最近使用与应用场景；下次识别时给相应词适度增强。Zipformer 热词需要受支持的 transducer 模型与 modified_beam_search，现有 greedy_search 配置不能声称已经启用学习。[sherpa 热词文档](https://k2-fsa.github.io/sherpa/onnx/hotwords/index.html)

第二层做**局部纠错学习**：用户在我们的预览/纠错面板把“沃克巴迪”改成“WorkBuddy”，关联原始识别、局部最终写法和语境；只在可解释的纠正中学习，歧义编辑、整段重写与模型自动改写不作为金标。不要求逐词询问；提供最近学习与撤销/删除入口。不能做无条件全局字符串替换。

第三层才考虑**个人声学适配**：只有真人数据积累后证明口音错误靠热词仍解决不了，才评估微调。固定权重不会因为多说几遍自动更新。8GB GPU 能做推理并不证明所有微调配置都可行。

系统级自动学习任意应用里的手动修改，通常比模型推理更难：UI Automation 支持、富文本及网页编辑器差异很大。首版保证在自身纠错面板闭环；后续只对已验证应用扩展，不能许诺“所有软件里改一下就自动学会”。默认本地保存必要词条，音频不长期保留；密码区域不学习，不扫描整篇文档。

## 开发顺序与验收

| 阶段 | 做什么 | 决策门槛（目标，未测得） |
|---|---|---|
| 0 证据校正 | 修复计分口径，用现有原始结果重算；补用户 50–100 句真人语料，另留未参与学习的测试句 | 单独报告中文 CER、英文 WER、混说术语命中、否定词/金额、标点与改坏率；不拿合成音频代替真人 |
| 1 最小闭环 | 可用热键、采集、浮窗、Zipformer 预览、句末提交与错误保留 | 开口到首字 P50 ≤500ms、P95 ≤1000ms；真人停顿/短词不丢尾；记事本、浏览器、聊天框、VS Code 实测 |
| 2 终稿选型 | 先对照 SenseVoice+CT / Nemotron / Fun-ASR-Nano，必要时补 Qwen0.6B；包含冷启动和 GPU 忙时 | 终稿相对首遍净改善；停止说话到提交 P50 ≤500ms、P95 ≤1000ms（含端点等待、推理与注入）；更准但更慢的方案单列，用户再权衡 |
| 3 个人学习 | 面板纠正→持久化→下次热词/重排；逐步接入可靠的目标应用纠错 | 重启后有效；新句里术语更准；普通同音词不被污染；每条学习可撤销 |
| 4 日常替代 | 与 Win+H 同麦克风同真人语料比较，长时间、休眠、焦点切换与内存压力 | 误字、纠错耗时、延迟、失败次数、空闲/录音/终稿资源均有记录，再确定日用默认 |

内存策略：轻量首遍尽量常驻，重终稿按需加载；若按空闲释放重模型，必须把再次加载时间计入下一句延迟。不要同时许诺“空闲 250MB”与“随时零冷启动”。当前剩余 RAM 偏少，先降低并行模型数量；没有证据要求现在购置硬件。

这一轮只形成路线图与官方资料研究，未重跑模型、未与 Win+H 做真人对照、未修复旧计分脚本，也未验证跨应用自动学习。最大的剩余不确定性是用户真人麦克风语音下的终稿质量和端到端延迟。
