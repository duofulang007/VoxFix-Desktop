# 标点重复与提前插入：根因与修复

- 版本：1.6.44.0 识别层（`app/recognize.py`，不改可执行文件，随 EXE 从磁盘加载生效）
- 日期：2026-10-23
- 状态：现行

## 现象

识别过程中草稿里就有句末标点，定稿后又多一个，出现 `。。`、`，，`，以及夹在已有标点旁的 `，。`。

## 根因：标点模型被喂了已经带标点的文本

SenseVoice INT8 在 `use_itn=False` 下**本身就会输出标点**，且几乎总是以句末标点结尾
（`work/p0` 前 60 条固定音频实测：59 条带尾部标点，58 条是 `。`、1 条是 `？`；14 条带内部标点；
0 条以标点开头）。草稿路径（`loop()` 里 `final=False`）不调用标点模型，所以
"草稿里提前出现的句号"就是识别结果自带的，不是标点层加的。

标点层只在定稿时运行，但 CT-Transformer 是按**无标点输入**训练的：它对每个位置都判一个标点，
遇到已有标点会在旁边再插一个，而不是跳过。实测（构造样例，非转写原文）：

| 输入 | 模型输出 | `punctuation_only` 判定 |
|---|---|---|
| `你好。` | `你好。。` | 放行 |
| `你好，` | `你好，。` | 放行 |
| `好的。` | `好的，。。` | 放行 |
| `你好，世界。` | `你好，，世界。` | 放行 |
| `我们明天，如果天气好，就去公园` | `我们明天，，如果天气好，就去公园。` | 放行 |

`punctuation_only()` 只校验"词元相同 + 原文非空白字符按序保留"，新插入的标点只要不破坏这两条就会通过，
所以契约 2 的守卫拦不住这种重复——守卫本身没写错，它保护的是"不许改写、不许删改已有标点"，
而不是"不许在已有标点旁再加一个"。旧 174 条固定音频上，旧逻辑有 **143/174 条**产出了相邻重复标点（共 200 处）。

## 修复

在 `SenseVoiceSession.punctuate()` 的守卫之后加一步 `drop_inserted_punctuation(text, result)`：

- 用贪心按序匹配把 `result` 里每个字符分成"原文自带"和"模型插入"两类；
- 只丢弃**模型插入的**、且与结果中相邻字符（前一位已保留字符或后一位字符）同为标点（`，。！？；：、,.!?;:`）的那些字符；
- 丢弃后再跑一次 `punctuation_only()`，不通过就退回原文。

因此它删的只是模型自己加的重复标点，原文任何一个字符（包括原本就有的标点、`.NET` 的点、小数）都不会被删；
模型在本来没有标点处加的标点依旧保留，`“好。”` 之外的句号、`？！` 这类有意义的连续标点也不受影响
（`”` 不在标点集合里，紧随其后的句号被视为有效新增）。

`punctuation_only()` 与契约 2 未改动；`dictionary.json`、模型权重、C# 送字链路均未改动。

## 生效条件：改完 `recognize.py` 必须重启 VoxFix

识别子进程只在 `Microphone.cs` 的 `Shown`（应用启动）和错误重试时创建，一个进程服务整轮使用期间的每次录音。
所以改完 `app/recognize.py` 后不重启应用，跑的还是编辑前加载进内存的旧模块，症状会一模一样地复现。
这次排查就踩到了这一点：应用与两个识别子进程在 21:34:30 启动，改动 21:51 落盘，用户听到的仍是旧代码。
重启（22:06:42 启动，子进程同为 22:06:42）之后才是新代码。

## 未验证与已知边界

- **没做**日常麦克风与真实输入框的主观验收；`--stream-test` 本轮跑过一次但被判为环境干扰
  （断言失败信息里测试输入框混进了零散字符，说明有真实键盘输入落进它的临时窗口），需在无人碰键鼠时单独复测。
  `--memory-test` 未跑（会移动鼠标）。
- 识别原文自带的连续标点（例如整段结尾的 `，。`）仍会原样保留，本轮不做清理，是否要清理需单独决策。
- 强制切分（`carry`）造成的半句仍会被标点模型补句末标点，这属于"在不该断的地方断句"，与本轮重复标点无关，未改。
- 跨分段的"前段以句末标点结尾、后段以标点开头"未做合并；实测 60 条固定音频里 0 条以标点开头，暂不引入规则。
- 旧 174 条只作辅助回归，未用于判断本次修复是否成立。
