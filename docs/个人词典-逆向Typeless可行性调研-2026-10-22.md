# 个人词典：逆向 Typeless 可行性调研

- 版本：1.6.29.0（调研基线，未改代码）
- 日期：2026-10-22
- 状态：现行（结论作为"做不做、做哪层"的决定依据）

> **2026-10-22 晚修正**：用户澄清 github→get up 发生在 **VoxFix 本体**，不是 Typeless——
> 对应微调权重的软件名缺口 + 草稿/定稿双解码覆盖（下表 VoxFix 一行的"不需要词典"随之修正）。
> 词典方案已实现，见[个人词典-解码后词表-2026-10-22.md](个人词典-解码后词表-2026-10-22.md)。
> 逆向 Typeless 不值得做的结论不变。

## 结论

1. **不逆向 Typeless**。词典的生效点在服务端（官方原话 "Typeless prioritizes them for higher accuracy"，
   是偏置不是本地替换），客户端里最多看到请求体；REA（morluto/rea）对 Windows 目标"部分功能仍在完善"，
   本机也未装 Typeless。即使解出机制，落到 SenseVoice 上也只有"解码后替换"一条路，而这条路不需要逆向。
2. **SenseVoice 不支持热词，这是架构硬约束**。sherpa-onnx 的 hotwords 只对 transducer
   （modified_beam_search）生效；FunASR 生态明确标注 "SenseVoice declares no hotword support"。
   解码期偏置物理上做不到。
3. **github → get up 不是"识别不准"，是二次加工改坏**。Typeless 是两段式（ASR 先上屏 → LLM 润色替换），
   第一瞬间闪出的"github"是 ASR 裸结果，后面被润色层改掉。这与我们 2026-10-21 润色实验同因：
   2B 润色净 +2 但改坏 3 句、4B 以上全负。词典治不了这个病——需要的是"别动已对的"，不是"把错的改对"。
4. 可落地的是**解码后词表**，分两级，成本约 50 行 Python + 一个 JSON，`Microphone.cs` 不用动。

## 现象归因

| 软件 | "先对后错"的成因 | 词典能否治 |
|---|---|---|
| Typeless | ASR 结果先上屏，LLM 润色层随后整句替换，把专名改成常见词 | 治不了根：词表进 prompt 只能降低概率，LLM 仍会改 |
| VoxFix | 没有润色层，无语义改写通路；但有 draft→final 双解码闪变：`recognize.py` 草稿用短音频、定稿用长音频各解一次，定稿覆盖预览 | 不需要词典；属契约 1 的 LCP 保护范畴 |

## SenseVoice 热词约束的证据

- sherpa-onnx 官方 API 文档：hotwords "supported only by transducer models decoded with
  decodingMethod 'modified_beam_search'"。SenseVoice 是非自回归单次前向，无重打分位置。
- FunASR 生产实践（nota-asr-server model-strategy）：SenseVoice 明确 `hotwords_not_supported`；
  带热词的是 Paraformer SeACo（decoder_bias，≤500 条）与 Fun-ASR-Nano（prompt 热词，LLM-ASR）。
- 换 Paraformer = 纯中文，英文整句与混说会更差（现基线混说本就 8/16）；换 Fun-ASR-Nano =
  回到已被否决的 LLM-ASR 路线（延迟、常驻内存）。两者都不取。

## 可落地方案（按风险分级）

- **L0 词表驱动的拆分合并与大小写规范**（零风险）：把已验证的"单字母合并"规则（p d f→pdf，149→151、0 改坏）
  扩展为词表驱动，如 `git hub → GitHub`。只处理空格拆分与大小写，不改发音。
- **L1 谐音映射**（需评测）：`get up → GitHub` 这类音近替换，必须带触发条件（如同句含技术语境词），
  否则会改坏 "I get up at seven"。判据：旧 174 条与 550 条新留出集零退化，判收益以未替换为基线。
- **L2 解码期偏置**：不可行（见上）。
- **自动添加**：Typeless 靠统计用户手工改词，我们经 UIA 拿不到编辑动作，性价比低。
  替代：跑 `tools/evaluate_sensevoice.py` 时把错例一键转成候选词条，人工确认入库。

## 实现位置与顺序坑

挂载点见下图（对话内示意图）：解码之后、标点之前是唯一可行位置。

- 必须在 `punctuate()` **之前**替换：`punctuation_only()` 按 token 正则比对原文与结果，
  `github`→`GitHub` 在标点之后做会被判 token 不等而退回原文，替换白做。
- 草稿与定稿**都要**过词表，否则预览 "get up"、定稿 "GitHub"，用户又看到一次闪变。
- 词表走 `models/` 同级的用户可编辑 JSON，运行时热读；不按评测词句硬编码（契约 3）。
