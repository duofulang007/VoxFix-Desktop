## 背景与归因修正

用户在 VoxFix 本体上观察到：说 "GitHub" 时草稿先闪出正确结果，随后被改成 "get up"。  
两点叠加：

1. 1.6.29.0 微调权重的已知缺口——软件名类术语（GitHub→git up、Python→pyython、API→a）  
   在较长音频的定稿解码中变差（[多源微调](多源真人语料微调SenseVoice-2026-10-22.md) 第 12 节）。
2. 草稿（短音频）与定稿（长音频）是两次独立解码，定稿覆盖预览；两侧输出不同即产生"先对后错"的闪变。

SenseVoice 架构不支持热词（sherpa-onnx hotwords 仅 transducer + modified_beam_search 有效），  
解码期偏置不可行，因此按调研结论实现**解码后词表**，给用户人工干预的入口。

## 实现

- 词表文件：项目根 `dictionary.json`（用户可编辑，随仓库带 GitHub 一条默认规则）。
- `app/recognize.py` 新增：
  - `load_dictionary()` / `apply_dictionary()` / `Dictionary`（按 `st_mtime_ns` 监视文件，  
    保存即生效，无需重启）。
  - 接入点在 `Recognition.loop()` 解码去标签之后、标点之前：草稿与定稿都过词表  
    （预览不会先闪正确结果再被定稿改掉），`punctuation_only()` 的 token 校验仍基于替换后的同一文本，  
    不会被 `github`→`GitHub` 误判。
- 匹配规则：大小写不敏感；纯 ASCII 词组加词边界（`(?<![A-Za-z0-9_])…(?![A-Za-z0-9_])`），  
  "get up" 不会命中 "forget upper" 内部；替换用回调注入，canonical 里的正则元字符按字面处理。
- 安全边界：
  - `context: "zh"` 的规则只在中英混说句（含 0x4E00–0x9FFF 汉字）替换，纯英文句保持原样，  
    防止改坏 "I get up at seven"；省略该字段则恒替换。
  - 文件缺失、JSON 损坏、条目非法时整层或单条自动跳过，识别链路不受影响。
  - 替换不触碰 `from` 之外的任何字符，与契约 3（不得按评测词句硬编码改写）不冲突：  
    机制是通用的、内容是用户可编辑的。

## 默认词表

```json
{ "rules": [ { "to": "GitHub",
               "from": ["get up", "git up", "git hub", "get hub", "gethub", "githup"],
               "context": "zh" } ] }
```

只内置用户实际报告的 GitHub 一条；Python、API 等其余软件名缺口由用户按需自行添加，  
不做批量预置（避免按评测词句预写规则）。

## 验证

- `tools/test_sensevoice.py` 新增 3 项（共 17 项全过）：词边界与 context 行为、  
  文件热更新与损坏恢复、管道级草稿/定稿替换；`test_language_guard` / `test_asr_scoring` /  
  `test_evaluation` 全过，均无需模型或设备。
- 词典层不改变音频、分段、送字与形变路径，未跑抢桌面的原生自检（用户正在使用机器）。

## 后续

- 若词表规模增长，可加"从评测错例一键生成候选词条"的工具入口。
