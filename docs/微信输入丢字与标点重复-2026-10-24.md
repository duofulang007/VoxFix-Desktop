# 微信输入丢字与标点重复

- 版本：1.6.51.0；日期：2026-10-24
- 状态：现行修复，微信实际测试草稿及原生回归通过；自然听写长时间验收未做

## 原因与同句对照

用户反馈微信输入框持续少字并出现问号/异常标点。直接使用固定测试文本，绕过识别、词典和标点模型，仍复现微信收字损坏，因此不能归为 ASR 模型准确率问题。

用户明确允许在文件传输助手空输入框写固定句，不点发送、不改已有草稿；第一次后又单独授权追加同句。原聊天的现有草稿保持不动，所有测试文字留在文件传输助手草稿中，没有发送。

| 输入方式 | 结果 |
|---|---|
| 原生产 VK_PACKET 批量送入 | 应有 `微信输入测试：你好，中文 ABC 123`，实得 `微信输入测试：：好，，文 ABC 123`；40/40 按键事件成功不代表字符正确 |
| 每字按下/释放后等 10ms | 同样损坏，不能用减速作为修复 |
| 只发送按下的诊断 | 错误重复首字，不采用；随后释放虚拟 VK_PACKET，未将该路径接入生产 |
| 同步 WM_CHAR | 同句逐字完整 |
| 正式后端追加同句，再退格并重写本次末字 | 44/44 对应事件单位完成；UIA 读取与「原测试草稿＋同句」严格相等，长度 100→120，先前草稿完整保留 |

一次诊断因输入框已非空被自动审批阻止；获得用户明确追加授权、核对只有测试文字后才继续。对照中曾因点击输入框让光标落到测试内容中间，后续先移到末尾，再按原文前缀和完整结果严格验收，不将光标位置错误的那次当作成功验收。

实际控件为微信 Qt51514QWindowIcon / `mmui::ChatInputField`，没有可单独送字的原生子 HWND，GUI 焦点是微信顶层窗口。证据摘要为 `work/wechat-input-comparison-20261024.json`，只保存固定测试句及计数，不含联系人或私人转写。实际探针日志在 `work/target-probe.txt`，该文件也含历史诊断，须按本轮时间筛选。

## 修复范围

`app/Microphone.cs` 的追加、草稿修订及明确授权的 `--target-probe --type` 共用 `Native.SendToTarget`。只对进程名 Weixin/WeChat 且类名以 Qt 开头的窗口使用 `SendCharacterMessages`；其他窗口、WeChatAppEx/Chromium 不误用该路径，继续原 SendInput。

字符按 WM_CHAR 同步处理，草稿退格使用同步 Backspace down/up，再送新字符，避免把退格留在异步队列而先写入新文字。沿用原送字层的成对事件计数口径以正确记录删除/插入前缀；每对输入前检查前台、焦点和用户编辑保护。发送超时 80ms；失败停止并由现有管线保留缓存，不尝试另一通道重发，避免超时后重复插字。拒绝把原文 CR/LF 当微信发送动作，不使用剪贴板。

Windows 的 Unicode 模拟按键经 VK_PACKET 和 TranslateMessage 转成 WM_CHAR，这个机制见 [Microsoft KEYBDINPUT](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-keybdinput)。该文解释机制，不证明微信问题；微信行为结论来自本机同句实测，不推广为所有 Qt 程序都有同样问题。
