## 决策

用户确认：错法**不收敛**（"每次变着花样错"），词表穷举路线不够稳；
选择**自研解码期热词偏置**（方案二）。30–50ms 量级的解码开销可接受，以延迟基准实测为准。
词典层（1.6.30.0）保留作最后兜底，两层并存。

## 预期管理（与用户对齐的边界）

- 偏置**不会自动发现错词**：词表仍需人工录入（后续做"纠错即录入"工具，偏置与词典共用）。
- **不是 100% 对**：偏置挪概率，强度低则漏网、高则误插（未念的词被写进结果）；
  强度必须过评测闸门，不能只看专项词。
- 收益形态：录入一个词后，其各种念法/错法整体被压向正确写法，不再需要逐个枚举错法。

## 已完成的可行性探测（2026-10-22）

- `models/sensevoice/model.int8.onnx` 输入输出签名（onnxruntime 1.31.0，清华镜像装入 `.venv`）：
  - 输入 `x [N, T, 560]`（= 80 维 fbank × LFR 7 帧堆叠）、`x_length`、`language`、`text_norm`；
  - 输出 `logits [N, T, 25055]`——**逐帧 CTC logits 可得**，偏置挂载点存在。
- 结论：接口可行。特征侧需在 Python 复刻 80 维 fbank → LFR(7/6) → am.mvn，
  与 sherpa 同音频逐字对齐后即打通（Phase 0 的核心验证）。

## 技术方案

1. **Python 解码器**：onnxruntime 直接跑生产 INT8 图，CTC 贪心解码复刻 sherpa 输出
   （去掉 `<|tag|>` 后逐字一致为过）。
2. **热词偏置**：canonical 经 `tokens.txt` 切成 token 序列建 trie；解码时维护各热词前缀状态，
   前缀命中帧对下一 token 的 logits 加偏置（CTC contextual biasing，SeACo 同族思路）。
3. **救援通道形态（默认候选）**：生产主路径不变仍走 sherpa；解码完成后若输出含与热词
   读音接近的片段，才用偏置解码器复解该段。未命中的句子零开销，命中时 +20–100ms。
4. 词表来源：`dictionary.json` 扩展热词字段，录入工具（纠错即录入）后续统一供给。

## 延迟预算（立项判据）

当前出字延迟 ≈ 等 550ms 音频（大头）+ 解码 20–100ms + 送字；偏置查表为每帧微秒级可忽略。
风险在 Python 解码实现本身，估 1.5–2×（短句 p50 20ms → 30–50ms），落在总账中应不可感知。
**实测说了算，不拍脑袋。**

## 阶段与闸门（任一不过即停，词典层兜底）

| 阶段 | 内容 | 闸门 | 预估 |
|---|---|---|---|
| P0 | fbank/LFR/mvn 复刻 + 同音频与 sherpa 逐字对齐；解码延迟对照基准 | 输出一致；解码 ≤2× sherpa | 1–2 天 |
| P1 | trie 偏置解码；专项术语集（用户录 20+ 词）+ 封存 1,314 + 新留出 550 | 软件名专项显著提升；三套评测零回归 | 2–3 天 |
| P2 | 强度调参、延迟优化、救援通道接线、录入工具 | 短句 p50 不退化；用户实测验收 | 2–3 天 |

## 风险

- 特征复刻偏差（fbank 参数/逐帧对齐）导致 P0 不过 → 换 kaldi-native-fbank pip 包或改从 FunASR 侧导出带前置特征图。
- 偏置过强引入误插 → P1 的三套评测 + 专项集双向把关，强度按词可配。
- int8 图在 ORT 与 sherpa 内置 ORT 版本间的数值差异 → 以逐字一致为验收，差异大则换 sherpa 同版本 ORT。
- 工程量超预期 → 救援通道形态允许只对含疑似热词的段启用偏置解码，主路径永不回退。
