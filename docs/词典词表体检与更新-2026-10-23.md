# 词典词表体检：按 R5 的错法更新默认词表

- 版本：1.6.44.0（词典内容变更，未改代码、未改 EXE）
- 日期：2026-10-23
- 状态：历史；当时词表与采用口径已由[个人词典统一规则](个人词典统一规则-2026-10-24.md)取代，以下保留 R5 诊断与原始结果。
- 前置：[从评测里挑词（1.6.40.0）](词表补词与整段话判断-2026-10-23.md)、[R5 模型启用](R5模型启用-2026-10-23.md)

## 为什么做

`dictionary.json` 里的 `from` 侧是**旧模型输出**的记录：1.6.40.0 那批错法（`cotland`、`git up`、`Jason`…）
来自 R4 之前的微调权重。1.6.44.0 换成 R5 之后没人重新核对过，用户提出两条：

1. 重跑测试，看哪些词是明显该进词典的；
2. 词典里记的错法可能已经过时，因为那是旧模型跑出来的。

## 怎么测

要判断"错法是否过时"，不能在生产口径上测——词表会把错误就地改对，看不到原始输出。
所以先把词典整个关掉（`rules` 与 `hotwords` 都为空），用当前生产权重重跑：

- 包装脚本 `work/dict-audit-20261023/eval_nodict.py`：与 `tools/evaluate_sensevoice.py` 同一条管线，
  只把每个 `Recognition` 的 `Dictionary` 指向一个不存在的路径（`load_dictionary` 失败即返回空），
  不改任何生产源码。
- 权重 `models/sensevoice/model.int8.onnx`，SHA-256 `a002044f…`（R5 INT8）。

裸识别基线（2026-10-23 22:20–22:26）：

| 语料 | 条数 | 整句 |
|---|---:|---:|
| 旧 174 条 | 174 | 137 |
| 术语探针（Python / Java） | 10 | 8 |
| ASCEND 测试集 | 1,130 | 415 |
| 封存 1,314（原速） | 1,314 | 654 |
| 新留出 840 | 840 | 508 |

然后把现词典逐条、逐变体套回这些裸文本（`work/dict-audit-20261023/variant_audit.py`），
统计每个错法命中几次、改好几条、改坏几条。

## 结论一：旧错法确实大面积失效

在 3,468 条裸文本上（五份语料合计），旧词典 49 个 `from` 变体里只有 10 个还会命中，
其余 39 个**一次都没出现**。其中真正属于"被新模型取代"的 24 个：

| 词 | 规则里记的旧错法 | R5 实际错成 | 旧错法命中 |
|---|---|---|---:|
| Kotlin | `cotland`、`coland`、`codelin` | `codetland`、`Klin` | 0 |
| GitHub | `gitthub`、`kitthub`、`get up`、`git up` | `Gthub` ×2 | 0 |
| JSON | `Jason`、`jason`、`J son`、`j sen`、`j-son`、`js on` | `J SO N`（单字母被空格拆开） | 0 |
| API | `a p i`、`api i`、`api` | `A P`、`A`（丢字母） | 0 |
| VoxFix | `voox fix`、`voxfix`、`box fix`、`vo fix` | 仍是 `vox fix`、`v fix` | 后四条 0 |

剩下 15 个 0 命中的变体属于**语料没覆盖**，不是模型变了：`Codex` 的 12 个变体（五份语料里 Codex 出现 0 次）、
`p d f` / `wi fi` / `why fi`（没有拆字样本）。这类不能判过时。

## 结论二：没有一条变体在改坏

`fix` / `break` 统计里，这 49 个变体在 3,468 条上 **改坏 0 条**。所以这次不做删减：
删掉 0 命中的旧错法收益为零，但它仍是长尾口音（粤语 20 条覆盖不足）的兜底，成本也是零。
真正要处理的是"新错法没被覆盖"和"写法本身是错的"。

## 结论三：词典自己写错了一个词

`{ "to": "Github" }` 输出的就是 `Github`，不是 `GitHub`。评测按小写比较单位，所以这个问题
在任何报告里都看不出来，但用户看到的是错拼写。已改为 `GitHub`（`hotwords` 同步）。

## 改了什么

| 词 | 变更 |
|---|---|
| GitHub | `to` 由 `Github` 更正为 `GitHub`；`from` 追加 `gthub` |
| Kotlin | 追加 `codetland`、`klin`（R5 实测错法） |
| JSON | 追加 `j so n`（修 `J SO N` 这种单字母拆开） |
| Java | **新增词条**：`javava`、`java`；`hotwords` 追加 `Java` |

`context` 保持不变：JSON、Codex、git status、git commit、sol、什么、GitHub 仍是 `zh`（7 条），
Python、API、PDF、WiFi、VoxFix、Kotlin、Java 不写 `context`（7 条，任何语言都规范写法）。

### 顺带修一个一直红着的测试

`tools/test_hotwords.py` 的 `test_pipeline_without_hotwords_never_touches_the_decoder` 用
"请把代码提交到gitthub"当输入，断言输出不变。1.6.40.0 把 `gitthub` 加进词表之后，这句话必然被改成
`Github`，所以这条断言从那时起就是红的（旧词表下同样失败，与本次改动无关）。该用例要验证的是
"没配 `hotwords` 时救援通道不创建会话"，与词表替换无关，因此把输入换成不含词表写法的
"请把代码提交到仓库"，断言不变。14 项全过。

## 故意没加

| 词 / 变体 | 实测 | 不加的理由 |
|---|---|---|
| `ja`→Java | 术语探针 4 条里能救 1 条 | 会把"还有Ja Hardden啊"（James Harden 被截断）改成 `Java Hardden`，ASCEND 里还有"那个Ja every time"。人名截断比漏一个 Java 更常见。加之前实测过，见下节 |
| `a p`→API | 能修 word-15 的 `A P` | 会把 app 被拆开时的 `a p p` 改成 `API p`；规则层没有"后面不许再接单字母"的断言 |
| cache→`cash` | 仍错 | `cash` 是正常英文词 |
| TOEFL→`to` | sealed 里 2 次 | 输出只剩 `to`，改回来会毁掉所有英文句子 |
| voice→`voiceice` | 1 次 | 不是专有名词，重复音节属于模型问题 |

`ja` 的误伤是在第一版候选里发现的：离线回放显示 ASCEND 与封存集各有 1 条被改坏，去掉该变体后归零。
