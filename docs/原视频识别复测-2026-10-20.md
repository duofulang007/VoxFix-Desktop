# 原视频识别复测

用户确认：此前的大段错字来自电脑播放的视频，经麦克风收录。随后提供原视频 `fb681223f16f28053f03.mp4`，时长 131.029 秒，原音轨为 48kHz 双声道 AAC。

## 已核实的结论

直接在内存中将原音轨转成 16kHz 单声道 PCM，再经过当前日用 `Recognition` 流式协议，仍能复现大量同音字和英文术语错误。因此不能把此前的错误归因于扬声器、房间或麦克风，也不能要求用户更换日常输入方式来代替识别改进。没有用户当时的麦克风录音，无法量化外放采集额外增加了多少错误。

本轮一度添加了电脑声音来源菜单的源码草稿，用户指出多此一举后已完整撤回，未构建、未发布。日用程序仍为 1.3.1.0，SHA256 `366784E1015F10386D4C41698A7CE795853DA4A25A5793528FF6525DFDB6983D`；没有更改音量、系统默认设备或麦克风采集方式。

## 显卡候选 Qwen3-ASR-0.6B

下载并校验 `handy-computer/Qwen3-ASR-0.6B-gguf` 的 Q8_0 文件，850,423,456 字节，SHA256 `f081b2d5e23bd669d92cc331d722a8a0681943b8e6f34b48996fd5c319b5acd8`。使用现有 transcribe.cpp 0.4.0 的 Vulkan 后端，日志明确显示 `using vulkan backend: Vulkan0`。这只属于候选实验，日用程序仍用 Nemotron 的 CPU 后端。

同样按 20 秒固定窗口，未提供词表或视频字幕给模型：恢复了“宫殿”“Blender”“Kimi”“国模”“小试牛刀”，仍把“紫禁城”写成“紫金城 / 紫英城”，部分型号及“鹈鹕骑自行车”仍错。不能据几个命中就称整段通过。

首个 20 秒窗口耗时约 7797ms（含该次 Vulkan 推理的冷启动开销），后续完整 20 秒窗口约 458–564ms；少量讲话的窗口更快。总推理和模型生命周期约 11.4 秒，但音频窗口必须先收齐，因此这些数值不是首字延迟。另用 `tools/qwen_prefix_probe.py` 测真实音频节奏与重复前缀稳定性。

本地移植版本的[模型文档](https://github.com/handy-computer/transcribe.cpp/blob/main/docs/models/qwen3-asr.md)明确尚不支持实时流式接口。原始 Qwen 模型有其他流式推理路径，但不能据此声称本机现有这个接口已经支持。不能直接替换当前 `stream.feed()`。

按真实节奏每 400ms 重识别累计原音频、两次共同前缀提交的实验，三个片段热身后的首批稳定文字约为 1010 / 850 / 858ms。但三个片段均会改写已经确认的前文，首次触发分别在音频进度 4.4 / 6.8 / 2.0 秒。初始变化涉及逗号和句号；离线去掉这些格式变化再检查，仍有较晚的“他 / 它”和“跟大家说 / 跟他说”改写，不能简单清理标点就视为稳定。15 秒片段持续重复推理也出现处理跟不上 400ms 触发间隔的情况。

因此 Qwen 在本视频的部分词上更准、GPU 热身后也足够快，但当前这条“反复识别累计音频”的简易接法没有通过稳定上屏要求。本轮未将其发布为首遍升级，也没有通过回删用户正文来掩盖这些变化。实验数据为 `work/source-video-20261020/qwen-prefix-paced.json`。

## 复现与边界

`tools/video_asr_probe.py <原视频绝对路径> --engine current|native|beam|sensevoice`；结果在 `work/source-video-20261020/`。音轨只在内存解码，不导出录音；结果文本属于这次明确提供视频的离线评测，不是应用恢复未输入文字的功能。

当前首遍按每 100ms 音频投递，整段处理约 11.5 秒，解码 RTF 约 0.079。首个结果在音频进度 1100ms 出现；这是非实时投递的音频进度，不是实际开口到屏幕的耗时。二者不能混用。改进目标仍为中文/中英混说准确率、快速首字和少改写，没有达标的配置不接入日用程序。
